# RouteFlow 재출시 개발 계획

**목표**　처음 온 사람은 예시 여행으로 동선을 이해하고, 자기 계획이 있는 사람은 원하는 작업을 선택해 곧바로 편집을 시작한다.

**제품 기준**　[README의 개편 방향](../../../README.md#개편-방향). 첫 화면과 인증 전후의 이동 방식을 새로 설계한다. 기존 브라우저 ES 모듈, 엑셀 파서, 지도·경로 모듈, Node 24 이상 계정 서버와 SQLite 저장소는 재사용한다. 새 요구와 충돌하는 게스트 편집 동작은 의도적으로 변경한다.

## 1. 프로젝트 계획 및 기획

- [ ] 부산 하루 코스 하나로 세 가지 과업을 설계한다. 비회원은 다음 장소와 예상 이동 시간을 찾아본다. 회원은 보고 있던 코스를 복사하거나 자기 엑셀로 시작한다. 엑셀 없이 시작하는 사람에게는 빈 일정 만들기를 제공한다.
- [ ] 화면 상태를 비회원 예시, 로그인 진행·취소, 로그인한 내 여행, 지도 연결 실패로 나눠 각 상태의 첫 행동과 되돌아갈 위치를 정한다. 비회원의 공개 범위를 도시 예시로 한정하므로 기존 개인 여행 공유 링크의 처리와 기존 소유자의 데이터 회수 경로도 정한다.
- [ ] 데스크톱과 모바일 시안으로 과업을 직접 수행해 본 뒤 구현 범위를 고정한다. 첫 출시에 AI·예산·동행 기능의 개편은 포함하지 않는다.

## 2. 개발 환경 설정

- [ ] 새 작업 브랜치에서 npm ci, npm test, npm run build, npm run check:release로 기준 상태를 기록한다. 예시 데이터, 기존 엑셀 양식, 이전 버전의 브라우저 백업을 반복 검증용 입력으로 준비한다.
- [ ] 지도·로그인 연동을 대체할 수 있는 기존 브라우저 테스트 환경을 쓴다. 실제 서비스 검증용 계정·지도 키·SQLite 파일은 개발 환경과 스테이징에서 분리한다.

## 3. 배포 및 테스트 환경 준비

- [ ] 계정 서버를 실행할 수 있는 비공개 HTTPS 스테이징을 마련한다. production-server.js로 dist와 계정 API를 함께 제공하고, SQLite 데이터가 재배포 후 유지되는지 확인한다. 도메인, 호스팅 및 비용은 실제 서비스 개설 전에 정한다.
- [ ] 스테이징의 로그인 콜백과 운영자 제공 지도 키의 도메인 제한을 설정한다. 로그인 후 여행 한 건 저장·다시 열기와 지도 경로 조회를 실제 연결로 확인한다.

### 3-1. 초기 CI/CD 파이프라인

- [ ] .github/workflows/smoke.yml의 단위 테스트, 빌드·릴리스 점검, 브라우저 검사와 Lighthouse를 유지한다. 게스트 편집을 전제로 한 기존 검사는 로그인 전후의 기대 동작으로 교체하고 엑셀·정렬·백업 회귀 검사는 회원 여정에서 계속 실행한다.
- [ ] PR에서는 모의 연동으로 검증하고 병합 후 같은 커밋의 검증된 산출물을 스테이징에 배포한다. 운영 승격은 7단계 검증 후 진행한다. GitHub Pages 자동 배포는 중단 상태를 유지한다.

## 4. 프런트엔드 개발

- [ ] **첫 세로 단위는 부산 예시 하나.** index.html의 초기 진입을 분리하고 js/mapview.js의 핀·경로 표시를 연결한다. 직접 구성한 예시 일정과 구간별 이동수단·예상 시간으로 목록을 먼저 그린다. 지도 요청이 실패해도 목록과 구간 설명은 읽을 수 있어야 한다.
- [ ] 도시를 바꾸면 목록·핀·경로가 한꺼번에 전환되고, 이전 도시의 느린 응답은 현재 화면을 바꾸지 않아야 한다. 모바일에서 목록과 지도를 오갈 때 같은 장소가 선택되어야 한다. 이 흐름을 확인한 후 서울·도쿄 예시를 추가한다.
- [ ] 상단에는 엑셀 가져오기·빈 일정 만들기·로그인을, 코스 아래에는 해당 코스 복사를 둔다. js/account.js와 js/app.js에서 인증 직전 작업과 예시 ID를 기억한다. 취소하면 보던 예시로 돌아간다. 엑셀은 인증 완료 후 사용자가 파일 선택 버튼을 누를 수 있는 가져오기 화면으로 연결한다.
- [ ] 브라우저에 저장한 예전 여행은 명시적으로 복원·이관하도록 한다. 배포 도메인이 달라지면 기존 브라우저 저장소에 접근할 수 없으므로 동일 출처 복구 가능성과 사용자가 이미 내려받은 백업을 구분해 안내한다.

## 5. 백엔드 개발

- [ ] backend/api.js의 세션 조회와 Google OIDC를 활용한다. 최초 로그인 시 계정 생성, 재로그인 시 기존 여행 조회, 세션 만료 시 저장되지 않은 작업 복구를 확인한다.
- [ ] 기존 여행 생성·저장 API와 backend/store.js의 소유권·버전 검사를 재사용한다. 예시는 공통 읽기 데이터로 유지하고 개인 복사본만 수정한다. 중복 클릭·인증 복귀 재시도로 같은 코스가 두 번 생성되는 경우를 검증한다.
- [ ] 익명 상태의 예전 편집·가져오기 진입점과 공유 URL을 함께 점검한다. 로그아웃 후 다른 사용자가 이전 계정의 개인 여행을 열 수 없어야 한다. 운영자 지도 키로 기본 흐름을 마칠 수 있어야 한다.

## 6. 코드 리뷰 및 협업

- [ ] 리뷰는 각 변경에 붙인다. 부산 예시 탐색, 로그인 후 작업 복귀, 계정 저장·엑셀 호환, 출시 설정으로 PR을 나눈다. 각 PR에 재현할 사용자 과업, 전후 화면, 회귀 검사 결과를 기록한다.
- [ ] 리뷰어는 코스 복사본을 바꿔도 원본이 보존되는지, 로그인 후 같은 도시·작업으로 돌아오는지, 이전 엑셀이 읽히는지 직접 확인한다.

## 7. 테스트 및 최적화

- [ ] 단위 테스트는 예시 유효성·선택 상태·저장 규칙, Playwright는 도시 변경·인증 취소/성공·엑셀 가져오기·빈 일정·다시 열기를 담당한다. 지도 오류, 느린 연결, 새로고침, 중복 저장도 포함한다.
- [ ] 과거 백업을 복원해 빈 날짜·장소 메모·방문 순서가 보존되는지 확인한다. 운영과 같은 설정에서 Google 로그인과 지도 호출을 따로 점검한다.
- [ ] 초기 사용자에게 설명 없이 두 과업을 준다. ‘다음 장소까지 걸리는 시간 찾기’, ‘내 엑셀로 시작하기’. 멈춘 위치와 완료 여부를 기록해 고친다. 초기에 지도·엑셀·AI를 모두 내려받지 않도록 기존 지연 로딩을 점검하고 첫 화면 표시 시간과 방문당 지도 호출 수를 기준 버전과 비교한다.

## 8. 프로젝트 완료 및 유지보수

- [ ] 검증된 산출물을 회원 기능을 지원하는 운영 환경으로 승격한다. SQLite 백업·복원과 이전 앱 버전으로의 롤백을 스테이징에서 먼저 리허설한다.
- [ ] 배포 후 비회원 예시 열람, 로그인 후 코스 복사, 본인 엑셀 가져오기를 다시 확인하고 README의 개편 목표를 실제 이용 안내로 갱신한다.
- [ ] 초기에는 로그인 복귀 실패, 가져오기 실패, 계정 저장 오류, 지도 호출 비용을 우선 관찰한다. 사용자 일정과 파일 내용을 수집하지 않고 실패 단계를 파악한다. 예시 경로·예상 시간에는 갱신 시점을 기록한다.

**첫 구현 이정표**　부산 예시에서 장소를 누르면 같은 번호의 핀이 선택되고 구간을 누르면 예상 이동 시간이 보인다. 모바일에서 목록과 지도를 오가도 선택이 유지되고, 지도 연결이 실패해도 일정을 읽을 수 있다. 이 결과를 본 뒤 도시와 회원 기능을 확장한다.
